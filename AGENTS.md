# AGENTS.md: ocx-lan-filter

Инструкции для агентов, работающих с этим проектом. Общее описание и схема: [README.md](README.md).

## Что это

Один Python-файл без зависимостей (`filter.py`), который слушает `0.0.0.0:10200`, проверяет ключ и проксирует запросы
в локальный ocx (`127.0.0.1:10100`), подменяя модель `local-llm` на ту, что выбрана в `config.json`.
Запускается как launchd-агент `com.local.ocx-lan-filter`. CLI для управления: `lanmodel`.

## Главные правила

1. **Не кладите ключ в репозиторий, README, логи и ответы.** Ключ живёт только в
   `~/.local/share/ocx-lan-filter/key`. В `.gitignore` стоят `key`, `*.key`, `config.json`. Если нужно
   показать пользователю ключ, он сам выполнит `cat` этого файла.
2. **Не переводите ocx на `hostname: 0.0.0.0`.** Это ломает локальные codex и omp (нужен токен), а ключи ocx не
   ограничивают модели. Весь смысл проекта в том, что ocx остаётся на loopback.
3. **Каждый эндпоинт пропускает только свои алиасы.** Не добавляйте проксирование `/v1/models` из ocx, админских путей
   (`/api/*`), эндпоинтов управления или списка моделей. Белый список путей это `ALLOWED_POST` в `filter.py`.
4. **Алиас `local-llm` у эндпоинта `default` не меняем.** Клиентское устройство настроен на него. Менять можно целевую модель.
   Новые эндпоинты и алиасы добавлять можно (через приложение в строке меню или `config.json` v2), у каждого эндпоинта свой ключ.
5. Рабочий код выполняется из `~/.local/share/ocx-lan-filter/`, а не из этого репозитория (macOS TCC не даёт
   launchd читать `~/Documents`). Любая правка в репозитории не действует, пока не запущен `./install.sh`.

## Как сменить проксируемую модель

```sh
lanmodel list                 # нумерованный список, * отмечает текущую
lanmodel set 6                # по номеру
lanmodel set provider/model-id   # или по точному id из list
lanmodel test                 # реальный запрос, показывает, какая модель ответила
```

- Список берётся из `GET http://127.0.0.1:10100/v1/models`, поэтому выбрать можно только то, что ocx реально отдаёт.
  Неизвестный id отклоняется с кодом 1.
- Применяется сразу, перезапуск не нужен: `filter.py` читает `config.json` при каждом запросе
  (`upstream_model()`), а `lanmodel` пишет его атомарно (`os.replace`).
- Если модели нет в списке, её сначала надо добавить в ocx (`~/.opencodex/config.json`, затем `ocx sync` и
  `ocx restart`), а не править фильтр.
- Формат id в ocx: для chat-пути `<provider>/<model>` (со слэшем, как в `/v1/models`). Записи вида
  `<provider>-native/...` идут через Responses API. Фильтр шлёт их на `/v1/chat/completions`, и для некоторых моделей
  это не заработает. После смены всегда запускайте `lanmodel test`.
- Не все модели подходят: например, `provider-native/some-model` через chat-путь возвращает 502
  (`upstream stream ended before a terminal frame`). Предпочитайте записи `<provider>/...`.

## Команды

| Задача | Команда |
|---|---|
| установить / обновить после правки кода | `./install.sh` (идемпотентен, ключ и config не перезаписывает) |
| текущая модель | `lanmodel` |
| проверка здоровья по LAN | `curl -s http://<MAC_LAN_IP>:10200/healthz -H "Authorization: Bearer $(cat ~/.local/share/ocx-lan-filter/key)"` |
| состояние сервиса | `launchctl print gui/$(id -u)/com.local.ocx-lan-filter \| grep -E "state\|pid"` |
| перезапуск | `lanmodel restart` |
| логи | `tail -f ~/.local/share/ocx-lan-filter/filter.log` |
| порт слушается | `lsof -nP -iTCP:10200 -sTCP:LISTEN` |
| ocx жив | `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:10100/v1/models` |

В логе каждая строка вида `<ip> POST <путь> [<реальная модель>] -> <код> (req <б>, resp <б>, <с>, finish=<stop|length|->, done=<yes|no>, prompt=<n|-> completion=<n|->)` показывает, какая модель обслужила запрос, чем он закончился и сколько токенов потратил. `finish=-` значит маркер не найден в ответе (нестандартная форма). `done=no` на стриминге означает, что SSE-терминатор `[DONE]` не пришёл — поток оборван (апстрим или соединение с клиентом).

## Ротация ключа

```sh
python3 -c "import secrets;print('lan_'+secrets.token_urlsafe(32),end='')" > ~/.local/share/ocx-lan-filter/key
chmod 600 ~/.local/share/ocx-lan-filter/key
```

Ключ читается на каждый запрос, перезапуск не нужен. Старый ключ перестаёт работать немедленно, поэтому нужно
обновить ключ на клиентском устройстве.

## Проверка после любых изменений

Запустите и убедитесь, что все пункты совпадают с ожидаемым (`K` = содержимое файла ключа, `B` = `http://<MAC_LAN_IP>:10200`):

| Запрос | Ожидание |
|---|---|
| `GET $B/v1/models` без ключа | 401 |
| `GET $B/v1/models` с ключом | 200, одна запись `local-llm` |
| `POST $B/v1/chat/completions` c `"model":"local-llm"` | 200, ответ модели |
| то же с реальным именем модели или любой другой моделью | 403 |
| `GET $B/api/keys`, `POST $B/api/keys` | 404 |
| `curl http://<MAC_LAN_IP>:10100/v1/models` | нет соединения (ocx на loopback) |

Проверять нужно именно по LAN-адресу `<MAC_LAN_IP>`, а не по `127.0.0.1`, иначе можно не заметить проблему привязки.

## Устройство кода

- `filter.py`: `Handler.do_GET` (`/v1/models`, `/healthz`), `Handler.do_POST` (валидация, подмена модели, стриминг).
  Стриминг идёт чтением `resp.read1()` и записью кусками, `protocol_version = "HTTP/1.0"`, чтобы не нужно было
  оформлять chunked-ответ. Ключ сравнивается через `hmac.compare_digest`.
- `lanmodel`: `show`, `list`, `set`, `test`, `restart`. `test` ходит на `127.0.0.1:10200` с ключом из файла.
- `install.sh`: копирует файлы в `~/.local/share/ocx-lan-filter/` и `~/.local/bin/`, генерирует ключ и config только
  если их нет, рендерит plist из `launchd/*.template` и перерегистрирует сервис.

## Известные подводные камни

- Сервис умирает вместе с Mac (сон, выключение). Клиентское устройство получит таймаут. Это ожидаемо.
- При остановленном ocx фильтр отвечает `502 upstream unavailable`.
- Смена `FILTER_PORT` потребует править plist и настройки клиентского устройства. Порт `10200` зашит по умолчанию.
- Если IP Mac выдаёт DHCP и меняется, клиент получит таймаут. Закрепите IP на роутере. Частный Wi-Fi адрес «Вращающийся» меняет MAC, и резервирование ломается.
- Фильтр не ограничивает число запросов и не считает расход. Всё, что проходит, тратит квоту аккаунтов за ocx.
- Таймаут на ответ модели 900 с, тело запроса до 32 МБ (больше — 413 после draining тела, чтобы клиент получал JSON, а не RST).

## Приложение в строке меню (`menubar/`)

- Swift-пакет: `LanModelCore` (логика, без UI, покрыта тестами) и `LanModelBar` (SwiftUI). Приложение не проксирует трафик,
  оно пишет `config.json` атомарно и читает `runtime.json`. Новых портов и IPC нет, правило 3 не нарушается.
- Валидация конфига продублирована в `filter.py::validate` и `Validator.swift`. При правке правил меняйте оба и
  общие фикстуры `tests/fixtures/validation.json` (их читают оба набора тестов).
- Хосты слушателей ограничены `0.0.0.0` и `127.0.0.1`. Не расширяйте.
- Ключ не логируется и не показывается без явного действия; в Swift он обёрнут в `SecretKey`.
- Тесты: `python3 -m unittest discover -s tests -t tests` и `cd menubar && swift test`. Все идут на временных каталогах
  (`OCX_LAN_FILTER_HOME`) и свободных портах и не трогают рабочий сервис.
- После правки `filter.py` нужен `./install.sh`, после правки приложения `menubar/scripts/build_app.sh && install_app.sh`.
- `launchctl print` показывает сервис, `~/.local/share/ocx-lan-filter/runtime.json` показывает состояние каждого порта.
