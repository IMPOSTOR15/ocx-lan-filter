# LAN Model Proxy: menu bar приложение для ocx-lan-filter

Документ состоит из трёх частей: требования и решения (1–2), дизайн (3), архитектура (4–6), план тестирования (7), порядок работ (8).
Это план **и** журнал решений: если реализация расходится с планом, расхождение записывается в раздел 9.

## 1. Цель и границы

**Цель.** Нативное приложение macOS в строке меню, которое:

1. показывает, какая модель проксируется и под каким алиасом;
2. меняет модель/алиас и параметры эндпоинта без редактирования JSON и без перезапусков;
3. добавляет новые эндпоинты и алиасы;
4. показывает состояние сервиса и ocx и позволяет им управлять (установить, перезапустить, остановить).

**Не входит в проект:**

- Менять ocx и его конфиг. ocx остаётся на `127.0.0.1:10100`.
- Учёт расхода, rate limit, TLS. Это ограничения фильтра, они остаются.
- Публикация в App Store, нотаризация. Сборка ad-hoc подписью, локальная установка.

### Жёсткие ограничения (унаследованы из `AGENTS.md`)

| # | Ограничение | Как соблюдаем |
|---|---|---|
| R1 | Ключ нельзя класть в репозиторий, логи, UI-логи и ответы | Ключ только в файле с правами 600. В UI скрыт, показ и копирование по явному действию. В логи и ошибки не попадает |
| R2 | ocx остаётся на loopback | Приложение ничего не пишет в конфиг ocx. Только читает `GET /v1/models` |
| R3 | Каждый эндпоинт пропускает **только** свои алиасы | Белый список путей `ALLOWED_POST` не меняется. `/v1/models` отдаёт только алиасы этого эндпоинта, не каталог ocx |
| R4 | Алиас `local-llm` у существующего эндпоинта не ломаем | Миграция сохраняет `local-llm`, порт `10200` и ключ. Второе устройство ничего не замечает |
| R5 | Рабочий код исполняется из `~/.local/share/ocx-lan-filter/` (TCC) | Приложение ставит сервис через тот же `install.sh`, копия лежит внутри `.app` |
| R6 | Смена модели применяется мгновенно, без рестарта | Сохраняем конфиг атомарно, фильтр читает его на каждый запрос |

## 2. Ключевые решения

### D1. Control plane на Swift, data plane остаётся на Python

Фильтр уже работает, обкатан на 1 МБ-запросах со стримингом и обработкой обрывов. Переписывать его на Swift нет причины и есть риск регрессии. Приложение **не проксирует трафик**, оно только управляет конфигом и сервисом.
Следствие: падение или выход из приложения не прерывает работу прокси. Приложение можно закрыть, прокся останется.

*Отвергнуто:* встроить прокси в приложение (выход из приложения убивает прокси, плюс переписывание стриминга); Electron/Tauri (тяжелее, хуже интеграция с меню баром).

### D2. Нативный стек: SwiftUI + `MenuBarExtra`, SwiftPM без Xcode-проекта

- `MenuBarExtra` со стилем `.window` даёт полноценный SwiftUI-поповер.
- SwiftPM: сборка из командной строки (`swift build`), `.app` собирается скриптом. Это воспроизводимо и удобно агентам.
- `LSUIElement = true`: нет иконки в Dock, только значок в строке меню.
- Минимальная ОС macOS 14.

### D3. Единственный источник правды: `config.json` (схема v2)

Приложение и фильтр общаются **только через файлы**: конфиг (пишет приложение) и `runtime.json` (пишет фильтр). Нет IPC, нет админ-порта. Это сохраняет R3: наружу не появляется новых путей.

### D4. Модель данных: эндпоинт → набор алиасов

Эндпоинт — это сокет (хост+порт) со своим ключом и своим набором алиасов. Алиас — имя модели для клиента, привязанное к реальной модели ocx.

Для чего несколько эндпоинтов: разные ключи для разных машин (отозвать один, не трогая другие), разные порты, loopback-эндпоинт для локальных тестов.
Для чего несколько алиасов: клиент выбирает `fast`/`smart` на одном порту.

### D5. Горячая перезагрузка слушателей

Фильтр раз в секунду проверяет mtime `config.json`. При изменении сверяет желаемое и фактическое множество слушателей: новые поднимает, удалённые и изменившиеся (хост/порт) останавливает, остальные не трогает. Смена алиасов и моделей не затрагивает слушатель, она применяется на следующем запросе. Рестарт сервиса не нужен никогда, кроме обновления самого кода `filter.py`.

### D6. Отказоустойчивость конфига

- Невалидный конфиг не должен уронить сервис: фильтр оставляет **последний рабочий** и пишет ошибку в `runtime.json` и в лог.
- Приложение валидирует до записи и не даёт сохранить плохой конфиг.
- Запись атомарная (`tmp` + `rename`), перед первой записью v2 делается `config.json.bak-v1`.

### D7. Обратная совместимость (миграция)

Старый формат `{"upstream_model": "..."}` читается как эндпоинт `default` (порт из `FILTER_PORT`/10200, `0.0.0.0`, ключ `key`, алиас `local-llm`). Приложение при записи v2 дополнительно пишет зеркальное поле `upstream_model`. Тогда старая версия `filter.py` и старый `lanmodel` продолжают работать на новом конфиге. Это важно на период между обновлением приложения и обновлением сервиса.

## 3. Дизайн интерфейса

Принципы: основное действие (сменить модель) делается в один-два клика из поповера; редкие операции (порты, ключи, новые эндпоинты) живут на втором экране того же окна. Никаких отдельных окон, `.sheet`, `.popover`, `.alert`, `.confirmationDialog` и `Menu`: любое из них уводит фокус и закрывает окно `MenuBarExtra`; внешний вид нативный, системные цвета и SF Symbols, поддержка светлой и тёмной темы.

### 3.1 Значок в строке меню

| Состояние | Символ | Условие |
|---|---|---|
| Всё работает | `arrow.left.arrow.right.circle.fill` | сервис запущен, ocx отвечает, все включённые эндпоинты слушают |
| Частично | `exclamationmark.triangle.fill` (жёлтый) | есть предупреждения: модель отсутствует в ocx, эндпоинт не поднялся, нужно обновить сервис |
| Недоступно | `xmark.circle.fill` (красный) | сервис остановлен или не установлен, ocx не отвечает |
| Остановлен вручную | `pause.circle` | все эндпоинты выключены |

### 3.2 Поповер (клик по значку), ширина 380 pt

```
┌──────────────────────────────────────────────┐
│ LAN Model Proxy              ● Работает      │
│ ocx 127.0.0.1:10100 ● · 42 модели            │
├──────────────────────────────────────────────┤
│ ● Home laptop                      [ вкл ]   │
│   http://<MAC_LAN_IP>:10200/v1   ⧉           │
│   local-llm  →  some-model  ⌄     │
│   fast       →  deepseek-v4-flash      ⌄  ⚠ │
│   [Проверить] [Ключ ⧉]        [Изменить…]    │
├──────────────────────────────────────────────┤
│ ○ Только этот Mac (выкл)           [ выкл ]  │
│   127.0.0.1:10201                            │
├──────────────────────────────────────────────┤
│ ＋ Новый эндпоинт…                           │
│ Редактор эндпоинтов…                         │
│ ───                                          │
│ Перезапустить сервис   Открыть лог           │
│ Запускать при входе  ☐        Выйти          │
└──────────────────────────────────────────────┘
```

- Строка `алиас → модель`: нажатие на модель открывает меню выбора из списка ocx (с поиском, текущая отмечена). Выбор применяется сразу.
- ⚠ рядом с моделью: модели нет в каталоге ocx. Подсказка объясняет причину.
- «Проверить» отправляет реальный запрос через сам эндпоинт и показывает результат (`ok`, время, что ответила за модель) или текст ошибки.
- Ключ: кнопка копирует в буфер обмена, на экране ключ не показывается. Буфер очищается через 60 с, если там всё ещё ключ.
- Базовый URL строится по IP интерфейса `en0`. Если IP нет, показывается `<ip>` и подсказка.

Особые состояния поповера:

| Состояние | Что видит пользователь |
|---|---|
| Сервис не установлен | Баннер «Сервис не установлен» + кнопка «Установить» (запускает встроенный `install.sh`) |
| Версия сервиса устарела | Баннер «Нужно обновить сервис (v1 → v2)» + кнопка «Обновить» |
| ocx недоступен | Красный индикатор в шапке; выбор модели недоступен, но можно ввести id вручную в редакторе |
| Конфиг невалиден (внешняя правка) | Баннер с текстом ошибки, кнопка «Открыть файл»; фильтр работает на последнем рабочем конфиге |

### 3.3 Единое окно (400×540 pt)

Одно окно `MenuBarExtra(.window)`, фиксированная ширина 400 pt и высота 540 pt, содержимое скроллится внутри. Состояние навигации и черновик хранятся в `UIState`, а не во view, поэтому закрытие окна ничего не теряет. Экраны (`RootView`):

| Экран | Что на нём |
|---|---|
| Список (`ListScreen`) | Шапка со статусом и «+», баннеры предупреждений, карточки эндпоинтов (включение, URL, алиас → кнопка модели, значки: URL, curl, ключ, проверка, «Изменить…»), подвал: автозапуск, перезапуск, лог, выход |
| Форма (`FormScreen`) | Общее, Сеть (сегмент «Вся сеть / Этот Mac», порт), Ключ (показать на 15 с, копировать, сменить), Алиасы (имя, модель, контекст, удалить), Подключение (URL, curl), «Удалить эндпоинт». Шапка: «Отменить», заголовок, «Сохранить» |
| Выбор модели (`PickerScreen`) | Поиск, ↑/↓ и Return, строка «Использовать «…»» для своего id, галка у текущей модели; выбор сразу пишет в конфиг (из списка) или в черновик (из формы) и возвращает назад |

Подтверждения (отмена правок, удаление, смена ключа, конфликт файла, перезапуск) показываются нижней панелью `ConfirmBar` внутри окна, остальное содержимое при этом недоступно. Esc и ⌘[ ведут назад: закрывают подтверждение, затем возвращают на предыдущий экран.

Ошибки валидации показываются под полем и блокируют «Сохранить». При изменении порта/доступа показывается предупреждение «Клиенты на старом адресе потеряют соединение». Если файл изменился на диске, пока форма открыта, при сохранении предлагается «Перечитать» или «Перезаписать».

### 3.4 Тексты и язык

Интерфейс на русском (язык пользователя). Строки собраны в одном месте (`Strings.swift`), чтобы потом локализовать.

### 3.5 Доступность

Все элементы подписаны (`accessibilityLabel`), полная работа с клавиатуры, статус не передаётся только цветом (всегда есть иконка/текст).

### 4.1 Схема `config.json` (v2)

```json
{
  "version": 2,
  "upstream": { "host": "127.0.0.1", "port": 10100 },
  "endpoints": [
    {
      "id": "default",
      "name": "Home laptop",
      "enabled": true,
      "host": "0.0.0.0",
      "port": 10200,
      "keyFile": "key",
      "aliases": [
        { "alias": "local-llm", "model": "provider/some-model", "contextLength": 1000000 }
      ]
    }
  ],
  "upstream_model": "provider/some-model"
}
```

Правила валидации (одинаковые в Swift и Python, проверяются тестами на общих фикстурах):

| Правило | Деталь |
|---|---|
| `version` | равно 2 (v1 мигрируется на лету) |
| `id` | `^[a-z0-9][a-z0-9-]{0,31}$`, уникален |
| `name` | 1–64 символа |
| `host` | `0.0.0.0` или `127.0.0.1` (другие значения не принимаются, чтобы не открыть лишний интерфейс) |
| `port` | 1024–65535, уникален среди **всех** эндпоинтов, не равен `upstream.port` |
| `keyFile` | относительный путь внутри state-каталога, без `..` и абсолютных путей |
| `aliases` | минимум 1; `alias` `^[A-Za-z0-9][A-Za-z0-9._:-]{0,63}$`, уникален внутри эндпоинта |
| `model` | непустая строка до 200 символов |
| `contextLength` | 1…10 000 000, по умолчанию 1 000 000 |

Уникальность портов проверяется среди всех эндпоинтов, а не только включённых. Так включение эндпоинта не может внезапно привести к конфликту.

### 4.2 Схема `runtime.json` (пишет фильтр, атомарно)

```json
{
  "filterVersion": 2, "pid": 4553, "startedAt": "2026-10-22T16:00:00",
  "configMtime": 1760000000.0, "configError": null,
  "endpoints": { "default": { "state": "listening", "host": "0.0.0.0", "port": 10200, "error": null } }
}
```

`state`: `listening` | `disabled` | `error` (с текстом, например «address already in use»).
Состояние `error` у одного эндпоинта не влияет на остальные.

### 4.3 Изменения в `filter.py`

1. `load_config()` возвращает нормализованный v2 (из v1 или v2). Кэш по mtime, при ошибке отдаётся предыдущий рабочий конфиг.
2. `ThreadingHTTPServer` получает `endpoint_id`; `Handler` на каждом запросе находит свой эндпоинт в актуальном конфиге.
3. Авторизация по ключу **этого** эндпоинта. Ключ  ищется в `keyFile`; если файла нет, запросы получают 401 и слушатель не поднимается (fail closed).
4. `do_POST`: `payload.model` ищется среди алиасов эндпоинта. Не нашли → 403 (как раньше). Нашли → подмена на `model`.
5. `GET /v1/models` отдаёт все алиасы эндпоинта с их `contextLength`; `GET /healthz` отдаёт `{"ok":true,"endpoint":id,"aliases":{alias:model}}` и для обратной совместимости `alias`/`upstream` для первого алиаса.
6. Supervisor с `reconcile()` и запись `runtime.json`.
7. `FILTER_VERSION = 2`. Переменная `OCX_LAN_FILTER_HOME` переопределяет state-каталог (нужна для тестов, по умолчанию прежний путь).
8. Стриминг и логирование не меняются. В строку лога добавляется `endpoint=<id>`.

### 4.4 Изменения в `lanmodel`

Читает и пишет v2. `lanmodel set` меняет модель первого алиаса эндпоинта `default`, как и раньше. Для v1 поведение прежнее. Добавлен вывод всех алиасов в `show`.

### 4.5 Компоненты `LanModelCore`

| Компонент | Ответственность | Зависимости (подменяются в тестах) |
|---|---|---|
| `Paths` | state-каталог, файлы | корень (по умолчанию `~/.local/share/ocx-lan-filter`) |
| `ProxyConfig`, `Endpoint`, `AliasMapping` | модель, `Codable`, миграция v1 | нет |
| `ConfigValidator` | правила из 4.1, возвращает список `ValidationIssue` с путём поля | нет |
| `ConfigStore` | load/save, атомарная запись, `.bak-v1`, обнаружение конфликта (хэш содержимого) | файловая система |
| `KeyStore` | генерация (`SecRandomCopyBytes`), права 600, чтение, ротация, маскирование | файловая система |
| `OCXClient` | `GET /v1/models`, таймаут, сортировка | `URLSession`-протокол |
| `RuntimeStatusReader` | разбор `runtime.json`, определение устаревания | файловая система |
| `ServiceController` | `launchctl print/kickstart/bootout`, разбор состояния; установка через `install.sh` | `CommandRunner` |
| `EndpointProbe` | тестовый запрос через эндпоинт (`/v1/chat/completions`, 1 токен-вопрос), `healthz` | `URLSession`-протокол |
| `NetworkInfo` | IPv4 интерфейса `en0` (`getifaddrs`) | нет |

`AppModel` лишь склеивает компоненты и публикует состояние для UI. Бизнес-логики во view нет.

### 4.6 Поток данных

1. **Смена модели из поповера:** `AppModel.setModel` → копия конфига → валидация → `ConfigStore.save` (атомарно) → фильтр подхватывает на следующем запросе. UI обновляется сразу (оптимистично), затем подтверждается перечитыванием файла.
2. **Новый эндпоинт:** редактор → валидация → `KeyStore.create(id)` → `ConfigStore.save` → через ≤1 с фильтр поднимает слушатель → `runtime.json` → UI показывает `listening`.
3. **Внешняя правка (`lanmodel set`):** опрос mtime каждые 3 с → перечитываем → UI обновляется, если нет несохранённых правок в редакторе.

### 4.7 Безопасность

- Ключи: `0600`, каталог `keys/` `0700`. Ключ не логируется, не попадает в сообщения ошибок, `description` модели ключа маскирует значение.
- Хост ограничен двумя значениями, лишние интерфейсы открыть нельзя.
- Приложение не поднимает собственных слушающих портов.
- Копия ключа в буфер: автоочистка через 60 с.
- Подпись ad-hoc, без песочницы (нужны `launchctl` и доступ к `~/.local/share`). Решение осознанное: приложение локальное, личное.

## 6. Установка и жизненный цикл

- `build_app.sh` собирает `LAN Model Proxy.app` (`LSUIElement`, bundle id `com.local.lanmodelbar`), кладёт в `Contents/Resources` копии `filter.py`, `lanmodel`, `install.sh`, `launchd/`.
- «Установить/Обновить сервис» в приложении запускает встроенный `install.sh` (идемпотентный, ключ и конфиг не затирает).
- «Запускать при входе» через `SMAppService.mainApp`.
- Приложение не требует прав администратора.
- Удаление: стереть `.app`; сервис остаётся и продолжает работать (команда удаления сервиса в README).

## 7. План тестирования

Уровни: unit (быстро, без сети) → интеграция (реальный `filter.py` на временном каталоге и фейковом апстриме) → контракт Swift↔Python → ручная приёмка (UI и живой сервис).
Все автоматические тесты идут на **временных каталогах и свободных портах**, не трогают рабочий сервис.

### 7.5 Критерии готовности

1. Все автотесты 7.1–7.3 зелёные (`python3 -m unittest`, `swift test`).
2. Чек-лист 7.4 пройден, кроме пунктов, требующих вмешательства человека (M-12, M-14), они отмечаются явно.
3. Таблица из `AGENTS.md` («Проверка после любых изменений») по LAN-адресу даёт ожидаемые результаты.
4. Документация (`README.md`, `AGENTS.md`) обновлена: новые правила про эндпоинты и алиасы.

## 8. Порядок работ

1. **Фильтр v2** (Python) + `lanmodel` + тесты P-*; проверка на временном каталоге.
2. **LanModelCore** + тесты S-*.
3. **Контрактные тесты** C-*.
4. **UI**: `AppModel`, поповер, редактор.
5. **Сборка `.app`**, скрипты установки.
6. **Развёртывание**: ждать паузу в трафике, `install.sh` (обновляет сервис), установка `.app`, прогон чек-листа M-*.
7. **Документация**.

Откат: `filter.py` и `config.json` бэкапятся перед развёртыванием; v1-совместимость (D7) позволяет вернуть старый `filter.py` без правки конфига.

## 9. Журнал расхождений с планом

- **Python 3.12 / бэклог сокета.** У `ThreadingHTTPServer` очередь `listen` равна 5, при всплеске из 12 параллельных запросов часть получала RST.
  Добавлен `Server.request_queue_size = 128` (тест `test_concurrent_requests`). Это попутно улучшает и боевое поведение.
- **Ключ сравнивается по ключу эндпоинта**, поэтому ключ одного эндпоинта на другом даёт 401 (P-05), что строже, чем в плане по умолчанию.
- **`saveDraft`** добавлен в `AppModel` (в плане не было): редактор сохраняет весь черновик за один раз, создаёт ключи новых эндпоинтов до записи и удаляет ключи убранных после неё. Покрыто S-12 и двумя дополнительными тестами.
- **Минимальная версия tools SwiftPM 5.9**, чтобы не зависеть от режима Swift 6 (строгая конкурентность) в UI-коде.
- **ScrollView в `MenuBarExtra(.window)` схлопывался в 0 по высоте**, из-за чего карточки эндпоинтов не показывались. Решение: у окна фиксированная высота, а `ScrollView` занимает `maxHeight: .infinity`. Найдено на скриншоте при ручной приёмке.
- **M-пункты**, выполненные автоматически на живом Mac: M-01, M-02, M-05 (на песочнице: 2 эндпоинта, новый ключ 200, чужой 401), M-13. Остальные (M-03/04 на боевом конфиге, M-09…M-12, M-14…M-16) нужно пройти руками, см. итог.
- **Боевой `config.json` остаётся в формате v1**, пока вы не сохраните что-либо в редакторе. Первое сохранение положит `config.json.bak-v1`.
- **Отдельное окно редактора убрано** по просьбе пользователя. Редактор, выбор модели и подтверждения перенесены внутрь единого окна (раздел 3.3). Дизайн сверен со спецификацией `frontend-specialist`, проверен скриншотами на песочнице (список, форма, выбор модели, подтверждение, создание эндпоинта с ключом). Из спецификации не взяты: недавние модели, пресеты контекста, автоскрытие результата проверки.
- **Оформление в стиле Liquid Glass (macOS 26+).** Стекло (`glassEffect`, `.glass`, `.glassProminent`) используется для управляющих элементов: круглые иконки-кнопки, капсулы выбора модели, кнопки «Изменить…», «Назад», «Сохранить», поиск, нижняя панель подтверждения. Контент (карточки эндпоинтов, секции формы, поля ввода) лежит на спокойной полупрозрачной заливке, чтобы стекло не накладывалось на стекло. Группы кнопок обёрнуты в `GlassEffectContainer`. Скролл мягко гаснет у краёв (`scrollEdgeEffectStyle(.soft)`). На macOS 14–15 те же места рисуются через `.regularMaterial` и `.bordered`. Все стили собраны в `Theme.swift`. Минимальная версия по-прежнему macOS 14.
